# Wiki Repos: GitHub-проекты в базе знаний

Зона `42-repos/` — карточки репозиториев, где владелец мейнтейнер или контрибьютор. Контракт зоны — `42-repos/README.md`, шаблон — `90-meta/templates/repo.md`.

## Когда применять

- «добавь в вики репозиторий X», «заведи карточку проекта на GitHub»;
- «что у меня в работе», «по каким репозиториям я мейнтейнер», «где я контрибьютор»;
- «занеси PR/релиз в журнал», «разбери этот PR в контексте проекта»;
- планово, раз в месяц: сверка зоны с GitHub.

## Сверка с GitHub

```bash
python3 90-meta/scripts/gh_repos_sync.py            # отчёт: новые, дрейф ролей, осиротевшие карточки
python3 90-meta/scripts/gh_repos_sync.py --write    # создать карточки для активных (push ≤ 365 дней)
python3 90-meta/scripts/gh_repos_sync.py --hub      # перегенерировать hub.md зоны
python3 90-meta/scripts/gh_repos_sync.py --json     # для обработки в коде
```

**`--write` — не по расписанию.** Зона наполняется точечно: карточка нужна там, где
проект нужен в голове, а не там, где `gh api` его вернул. Пакетная генерация делает
зону свалкой из зеркал и остывших репозиториев, после чего её приходится чистить
вместе с историей. Отчёт без `--write` безопасен и полезен всегда.

Правила, которые скрипт соблюдает и агент обязан соблюдать:

1. **Роль — из прав GitHub.** `admin|maintain` → `maintainer`, `push|triage` → `contributor`, `pull` → `watcher`. Не выводить роль из «звёздности», знакомства или активности.
2. **Чужие карточки не переписываются.** Скрипт только создаёт недостающие и сообщает о дрейфе. Правка существующей карточки — решение владельца (или агента по явной просьбе), с записью в `log.md`.
3. **Форки мимо.** По умолчанию исключаются: зеркало без собственных коммитов — не проект. Исключение — форк, где есть свои изменения (`upstream` + запись в журнале).
4. **Порог активности.** Карточки создаются для репозиториев с push за 365 дней; старше — только строка в хабе со `status: paused`. Не плодить карточки для заброшенного.

## Добавление репозитория вручную

1. Проверить, нет ли уже карточки: `grep -l "repo: owner/name" 42-repos/*.md`.
2. Взять метаданные из GitHub, не по памяти:

```bash
gh api repos/owner/name --jq '{full_name,description,language,topics,license:.license.spdx_id,archived,pushed_at,default_branch,stargazers_count}'
gh api repos/owner/name/collaborators/pravets/permission --jq '.permission'   # для чужого репозитория
```

3. Создать карточку по шаблону `repo.md`: `name` — что это и для кого, `repo`, `role`, `status`, `stack`.
4. Тело: `## Что это` — смысл проекта, не пересказ README; `## Моя роль` — что моё, что чужое.
5. Добавить ссылку из связанной страницы (`10-wiki`, `40-projects`, `50-drafts`), иначе карточка сирота.
6. `make index`, `log.md`.

## Событие в журнале

Append-only в `42-repos/log.md`, в конец, дата по возрастанию:

```
## [2026-11-22] pravets/checkushka | pr#37 merged — правило p2-EDT, 12 файлов
```

Одна строка на событие; подробности — в теле PR или в карточке, не в журнале. Разбор чужого PR (когда проект не твой) — отдельная заметка, если он дал знание: «что я понял про X» уходит в `10-wiki`, а в журнал остаётся ссылка.

## Разбор PR/issue в контексте проекта

```bash
gh pr view 412 --repo owner/name --json title,body,files,state,mergedAt,additions,deletions
gh pr diff 412 --repo owner/name | head -200
```

Что делать с результатом:

- **своё решение** (почему так, что отверг) → строка в `log.md` карточки репозитория;
- **новое знание о технологии** → страница `10-wiki` (или дополнение существующей), карточка репозитория — в `sources`;
- **задача на потом** → `50-drafts/<slug>/ideas.md` или `25-interactions`, не в карточку.

## Чего не делать

- Не копировать код и диффы в заметки — только ссылки и выводы.
- Не выдумывать роль, стек и даты: `gh api` отвечает за это, память — нет.
- Не создавать карточку для форка без собственных коммитов.
- Не править хаб `42-repos/README.md` руками — он генерируется.
