# Wiki Verify: не «в посте сказали», а проверено

Дисциплина против маркетинга и пересказов. Работает в двух режимах: **перед записью** (не пустить непроверенное в вики) и **аудитом** (проверить уже записанное).

Основание: большинство мусора в базе знаний приходит не из вранья источника, а из того, что пересказ приняли за первоисточник, а заявленное — за факт.

## Режим A: перед записью (основной)

Для каждого утверждения, которое собираешься записать:

1. **Источник — первоисточник или пересказ?** Рил, пост, статья-обзор — это пересказ. Первоисточник: репозиторий, документация, официальный API, сам продукт, закон.
2. **Чем проверить прямо сейчас?** Числа, версии, лицензии, авторство, даты — проверяемы живьём (рецепты ниже). Не проверил — так и пиши: «не проверено».
3. **Что это на самом деле стоит?** Вместо списка возможностей — trade-off: «работает так, требует вот этого, при таком-то условии не работает».

Правила записи:
- Проверенное — обычным текстом, со ссылкой на источник.
- Непроверенное — либо не пишем, либо пишем **явно помеченным**: «заявлено в источнике, не проверено».
- Число из источника, отличающееся от живого, — фиксируем **оба** («заявлено N, фактически M на дату»).
- Никогда не повышать статус: «не проверено» не превращается в «факт» при пересказе.

## Режим B: аудит существующего

1. Собрать утверждения страницы (или пачки): факты, числа, версии, характеристики, «поддерживает X».
2. Сверить каждое с полем `sources:` страницы: этот источник действительно утверждает это — или утверждение пришло из общего знания?
3. Проверить, что проверяемо (рецепты ниже).
4. Отчёт владельцу: что подтверждено, что не подтверждено, что устарело. Правки — **после** его решения (ревью-гейт), не молча.

## Рецепты живой проверки

| Что проверяем | Чем |
|---|---|
| Репозиторий: звёзды, лицензия, описание, последний push | `gh api repos/<owner>/<name> --jq '{stars:.stargazers_count,license:.license.spdx_id,pushed:.pushed_at}'` |
| Версия релиза | `gh api repos/<owner>/<name>/tags --jq '.[0:5][].name'` |
| **Заявленные возможности vs реальные** | клонировать и **читать код**, а не README: `git clone --depth 1`, затем `grep -rn` по модулям, реестрам, лимитам |
| Авторство / кто поддерживает | `gh api repos/<owner>/<name>/commits --jq '.[].commit.author.name'` |
| Термин из ASR-транскрипта | `_shared/scripts/verify_terms.py <транскрипт> <термин>` |
| Страница/докладка по ссылке | `web_extract`; недоступно — так и помечать |

**Главное правило:** README читается как заявление, код — как факт. Расхождение между ними и есть самый ценный результат проверки.

## Контракт вывода (и для отчёта, и для страницы)

- **Что подтверждено** — утверждение → источник → как проверено
- **Trade-offs, а не описания** — не «умеет X», а «X работает так, платим вот этим»
- **Flags** — во что не верить: маркетинг источника, пересказ вместо первоисточника, непроверенные числа, монетизированные рекомендации, устаревшее
- **Границы применимости** — при каких условиях это перестаёт работать
- **Что бы это подтвердило** — минимальная проверка, которой не хватает

Правила стиля: без воды; каждая строка должна сообщать то, чего читатель не увидит сам; **если секции нечего сказать — так и написать** («Ничего существенного») и идти дальше; ориентир — до ~500 слов на страницу.

## Грабли

- **Красивый README — не доказательство.** Заголовочные числа и «поддерживает N платформ» часто расходятся с реестром в коде.
- **«Бесплатно» и «обходит блокировки» — проверяемые утверждения**, а не оценки: смотри, что написано про серверные IP, прокси и лимиты, даже если это спрятано ниже рекламы.
- **Спонсорские блоки и UTM-метки** в рекомендациях = монетизированный совет; помечать как смещение источника.
- **Свои же прошлые записи — тоже пересказ.** Если страница писалась из рила, аудит её наравне с новыми.
- **Не превращать аудит в источник.** Вывод проверки — это анализ; в вики ссылаемся на первоисточник.
